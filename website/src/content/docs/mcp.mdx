The [`sysspec-mcp` package](https://www.npmjs.com/package/sysspec-mcp) gives
read-only MCP access to a spec tree, both to agents building against it and
to anyone who would rather ask the system a question than go looking for
the file. One TypeScript implementation sits behind every route in,
whether that is stdio for a local client or stateless streamable HTTP for a
hosted URL. There is no
write tool, and reads are confined to artifacts a service manifest
declares, so dropping a file into the tree does not silently expose it.

The server is a generic engine. The specs are per-repo data, pointed at
with `SPECS_DIR`.

:::tip[Useful before you build anything]
Connected to a client, these tools let anyone question a spec suite in
plain language. Who consumes this event? What does a customer have to
supply? What would this change break?
[Ask the specs](/ask-the-specs/) covers that use, which is most people's
first one.
:::

## The tools

| Tool | Use | Narrowing parameters |
| --- | --- | --- |
| `list_services()` | Discovery. Start here. | none |
| `get_service(name)` | Artifact index + produce/consume edges. No file contents. | none |
| `get_message_schema(service, message)` | One event payload, the cheap call. | omit `message` to list message and schema names |
| `get_acceptance_criteria(service)` | Gherkin, labelled binding. | `names_only` for the scenario index; `scenario` or `path` for one |
| `get_artifact(service, path)` | Any declared artifact, with its authority class. | `section` (RFC 6901 pointer) for one part; `max_bytes` |
| `trace_channel(address)` | Who produces and consumes it, i.e. who you break. | none |
| `search_specs(query)` | Matching lines, not whole files. | `kind`, `service`, `limit` (≤ 100) |

Responses are bounded and narrowly addressable. Any response that had to
cut content says so with a `truncated` flag; raise `limit`/`max_bytes`
only then.

A `get_acceptance_criteria` scenario match carries `rule_index` when the
scenario sits inside a Rule. `rules[rule_index]` is that Rule's block
(its line, description and Background), and a scenario stands alone as
`header` + `rules[rule_index]` + `gherkin`. The header holds the Feature
and its Background only. Parts that did not fit the budget are flagged
rather than sent: `header_omitted`, `gherkin_omitted`, `names_omitted`
and `unlisted_matches`.

## Run it locally

```bash
# stdio (what .mcp.json and the Claude plugin wire up)
SPECS_DIR=./specs npx -y sysspec-mcp

# streamable HTTP on a port
SPECS_DIR=./specs npx -y sysspec-mcp --transport http --host 0.0.0.0 --port 8080
```

Every flag has a container-friendly env equivalent: `SYSSPEC_MCP_TRANSPORT`,
`HOST`, `PORT`, `SYSSPEC_MCP_PATH` (the endpoint path, default `/mcp`) and
`SYSSPEC_MCP_ALLOWED_HOSTS` (see [Hardening](#hardening)).

Register it with a client:

```bash
claude mcp add sysspec --scope project \
  --env SPECS_DIR=/path/to/your-specs/specs \
  -- npx -y sysspec-mcp
```

## Serve it over a URL

HTTP mode is stateless. There is no session affinity, so it works behind
any load balancer or scale-to-zero platform. The MCP endpoint is `/mcp`;
`/` answers with a small info document. Deployment is host-agnostic:

- **Any Docker host, VPS or Coolify.** Deploy the
  `ghcr.io/hungovercoders/sysspec-mcp` image CI keeps current with the
  example specs, or build from `mcp/Dockerfile` with your own.
- **AWS.** App Runner or ECS pulling the image, port 8080.
- **Cloudflare.** Containers can run the same image, or a free-tier Worker
  adapter bundles the specs at deploy time with
  `cd mcp && npx wrangler deploy --config adapters/cloudflare/wrangler.jsonc`.

Connect from anywhere that can't spawn a local process (remote sessions, CI):

```bash
claude mcp add sysspec --scope project --transport http https://<your-deploy>/mcp
```

The example specs are served live at <a href={DEMO_MCP_URL}>{DEMO_MCP_URL}</a>.
Wire it up with the line above and start with `list_services()`.

Whichever route, verify with `/mcp` and then `list_services()`.

Once an endpoint is hosted, record it in the suite's `specs/system.yaml`:

```yaml
mcp: https://specs.example.com/mcp
```

The generated catalog reads that field and puts the URL on its **Ask these
specs** page, so readers can connect without being told how by anyone.

## Hardening

The tools are read-only and confined to declared artifacts, so the blast
radius of an open endpoint is "someone reads the specs". If the specs are
not public: put an authenticating proxy (Cloudflare Access, an ALB with
OIDC, …) in front of the URL, and set
`SYSSPEC_MCP_ALLOWED_HOSTS=mcp.example.com` to reject requests carrying any
other Host header (DNS-rebinding protection).
