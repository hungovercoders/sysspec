A spec suite is usually justified by what it does for *building*: agents
and engineers read the contracts over MCP, and gates hold implementations
to them. That is half of it. The same tools, pointed at the same specs,
make the system **answerable** by anyone, in plain language, without
opening a file.

- *"Who consumes `orders.placed.v2`?"*
- *"What does a customer have to supply to place an order?"*
- *"If we dropped `customer_id` from `OrderPlaced`, who breaks, and is that a major?"*
- *"Where is 'settled' defined, and does payments mean the same thing by it as orders?"*

Answering those questions usually means finding the right repo, finding
the right file, working out whether it is current, and then finding the
person who actually knows. Here each one is a sentence, answered from the
specs of record, which are versioned, gated and the same surface every
implementation is held to. Nobody has to fall back on memory or on code
that may have drifted from what was agreed.

## Who this is for

- **Product and delivery** ask what a service is responsible for, what it
  guarantees, and what it deliberately leaves open.
- **Analysts and data people** ask what an event carries, what is required,
  and what the data products promise.
- **Architects and tech leads** ask who depends on a channel, what a change
  would break, and whether an idea is modelled consistently across
  services.
- **Support and operations** ask what the system is *supposed* to do, which
  is the first thing you need when deciding whether behaviour is a bug.
- **New joiners** ask the obvious questions on their first morning.
- **Agents** use the same tools and get the same answers at implementation
  time.

The artifact that lets an agent build correctly is the artifact that lets
a person ask a good question, and you only have to maintain one of them.

## Try it on the live demo

The example suite is served publicly, so you can ask before you scaffold
anything:

```bash
claude mcp add sysspec --scope project \
  --transport http https://demo.sysspec.dev/mcp
```

Then `/mcp` to confirm, `list_services()` to open, and ask in your own
words. The <a href={DEMO_SITE_URL}>catalog</a> and the endpoint at <a
href={DEMO_MCP_URL}>{DEMO_MCP_URL}</a> are built from the same commit, so
what you read and what you are told cannot disagree.

## Point it at your own specs

Any checkout works; the server reads one directory and nothing else:

```bash
claude mcp add sysspec --scope project \
  --env SPECS_DIR=/path/to/your-specs/specs \
  -- npx -y sysspec-mcp
```

Once a team is asking regularly, host it once instead of everyone running a
process: `sysspec-mcp` serves streamable HTTP behind a URL (see
[the MCP server](/mcp/#serve-it-over-a-url)). Record the endpoint in
`specs/system.yaml`:

```yaml
mcp: https://specs.example.com/mcp
```

Your generated catalog's **Ask these specs** page then hands every reader
that URL, alongside starter questions drawn from your own services,
messages and scenarios.

## What it will not do

- **No writes.** There is no write tool. A conversation cannot amend a
  contract, because changing one is a deliberate, versioned act with its
  own gates.
- **No runtime.** These are specs of intent: what the system is meant to
  do, not what an instance did last Tuesday. No traffic, no incidents, no
  data.
- **No undeclared files.** Reads are confined to artifacts a service
  manifest declares, so dropping a file into the tree does not silently
  expose it.

If an implementation disagrees with an answer, that is a bug in the
implementation, and its [gates](/gates-and-ci/) should already be red.
