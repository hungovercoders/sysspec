## Specs that do double duty

sysspec is a system spec tool. You author intent — AsyncAPI, OpenAPI, ODCS
data contracts and Gherkin acceptance criteria — and those specs work twice:

<CardGrid>
  <Card title="Context to build from" icon="open-book">
    Engineers and AI agents read the specs over MCP at implementation time
    instead of guessing from code. Seven narrow, read-only tools serve
    exactly the artifact, message, or scenario needed.
  </Card>
  <Card title="Deterministic gates" icon="approve-check">
    The same specs are packaged and consumed by implementations for local and
    CI testing. They cannot be quietly amended to make failing code pass,
    because they live and version separately from every implementation.
  </Card>
</CardGrid>

This is not documentation of what you have. Specs written next to an
implementation drift toward whatever the code happens to do; sysspec inverts
that. Intent is authored once, versioned deliberately, reached only through
tools, and enforced mechanically — the implementation conforms to the spec,
never the other way round.
