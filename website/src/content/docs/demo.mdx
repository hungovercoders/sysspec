The sysspec repo carries a living example: **sysspec demo**, the
`orders`/`payments` spec suite in the Commerce domain, which doubles as the
toolkit's regression suite, so every toolkit change has to keep it green.
It deploys on every merge to main:

- **The spec catalog** is the generated docs site at the Worker root, with
  service overviews, OpenAPI/AsyncAPI/data-contract renderings, acceptance
  criteria and the interactive system graph.
- **The MCP endpoint** is the same specs served by `sysspec-mcp` over
  streamable HTTP at `/mcp`.
- **The mocks** are the same contracts and example fixtures, served on a
  Worker of their own: REST responses and ambient CloudEvents over
  WebSocket, so a consumer can be built against this suite with nothing
  installed.

All three are built from the same spec commit, and every pull request
against the specs gets its own stable preview URL of the whole system.

The mock index lists every URL it serves. The REST mocks answer on
`/rest/<Title>/<version>/…` and the event channels publish the example
CloudEvents on `/api/ws/<Title>/<version>/<operation>`, both with the
titles and versions the contracts declare:

```bash
curl https://mocks.sysspec.dev/rest/Orders+API/3.2.0/orders/11111111-1111-1111-1111-111111111111
```

They are the same mocks `task mocks:serve` runs locally, held to the same
example suite by `sysspec mocks test` on every deploy. They are stateless
and read-only: a POST returns its example, it does not change what a later
GET answers. Build a consumer against a pin (see
[contracts.lock](/contracts-lock/)) rather than against the hosted URL,
which moves with main.

Connect a client to the endpoint and start with `list_services()`:

```bash
claude mcp add sysspec --scope project --transport http https://demo.sysspec.dev/mcp
```

Then ask things like:

- "What fields are on OrderPlaced?"
- "Who consumes payments.settled.v2?"
- "What does a customer have to supply to place an order?"
- Ask it to drop `customer_id` from OrderPlaced, and it should refuse and
  cite the consumers

You do not need to be building anything to get value from that endpoint;
see [Ask the specs](/ask-the-specs/).

This website and the demo are separate deployments: the demo renders a
*spec suite* (what `sysspec init` gives you for your own specs), while this
site documents the tool itself.

Each catalog is annotated for the system it describes: `specs/system.yaml`
names the system, its business domain, its event namespace and the MCP
endpoint it is served on, and the generated site carries them in its title,
header, footer and its **Ask these specs** page. The demo reads
"sysspec demo · Commerce · `com.hungovercoders`"; yours reads as whatever
you scaffolded with `sysspec init my-specs --org com.acme --system "Acme
Commerce" --domain Commerce`.
